e2e의 남은 병목은 모델이 아니라 시험이다. macOS에서 git shim만 우회해도 전체 시험이 27% 빨라졌고, 다음은 검증 실패를 새 시도 대신 수리로 처리하는 일이다.

1차 [[e2e-time-reduction]](v7·v9에서 구현)의 후속이다. 그 뒤 시험이 약 560개에서 1,459개로 늘어 절감분을 상당히 잠식했다.

## 측정
**v10 claude worker 141분의 구성**: 모델(API) 50분(35%), 전체 시험 대기 약 61분(43%), 좁은 시험 24분(17%), 나머지 6분. v9는 278분 중 모델 113분이다.

**시험이 느린 이유**: 프로세스 생성 비용이 크다. 전체 시험 CPU는 `sys`가 `user`보다 많다(부하 없을 때 968초 대 880초). `test_ticket_verify.py`는 시험 28개에 git 프로세스 5,606개를 띄운다.

**git 변형 A/B**(복제본, 시험 파일은 부하 2 안팎, 전체 시험은 부하 3–7, 2026-11-05 18시대):

| 변형 | `test_ticket_verify.py`(2회) | 전체 시험 6프로세스 |
|---|---|---|
| 기준(`/usr/bin/git`) | 55.5, 55.7초 | 387.1, 385.8초 |
| `xcrun --find git`의 디렉터리를 PATH 앞에 | 38.8, 38.7초 | 281.7, 280.4초 |
| 자동 maintenance 끔 | 54.4, 54.9초 | 안 잼 |
| fsync 끔(`GIT_TEST_FSYNC=0`) | 55.5, 56.2초 | 안 잼 |
| 셋 다 | 37.6, 37.9초 | 안 잼 |

전체 시험은 ABBA 순서로 돌렸고 시험 1,459개가 네 번 모두 통과했다. 효과는 거의 전부 shim 우회에서 나온다.

**일정 재생**(v9·v10의 단계 시간으로 의존, 자리, 직렬 검증을 흉내 냄. 기준값 303분 대 실제 301분, 132분 대 132분. 어림값이다):

| 시나리오 | v9 | v10 |
|---|---|---|
| git 직접 경로(측정값 0.73배 적용) | -12% | -16% |
| 위 + worker·수정 worker의 전체 시험 제거 | -25% | -30% |
| 위 + 검증 실패 재시도 없음 | -51% | -30% |
| 시험 2배 빠르게(참고) | -22% | -26% |
| 같은 파일 순서 제거(충돌 0 가정, 상한) | -23% | 0% |
| 마무리 main 검증 생략 | -2% | -5% |
| 모델 시간 20% 감소 | -5% | -3% |
| `max_workers` 4 또는 6 | 0% | 0% |
| 검증을 루프 밖으로 | -1% | 0% |

재생은 시험을 뺀 뒤 검증 실패가 늘어나는 비용을 넣지 않았다. 충돌이나 수리 시간도 넣지 않았다.

**검증 실패 재시도의 원인**: 코드 결함보다 시험 쪽 문제가 많다. 지금은 worktree를 새로 만들어 처음부터 다시 구현한다.
- v9 03·05·06: 모두 같은 불안정한 시험(`test_network_wait`, 이미 고침). 재시도가 v9 시간의 최대 37%다.
- v8 12, v11 09: skill 글 단어 상한 시험. v11은 마지막 integration도 `test_adopt_skill`로 실패해 티켓 11을 더 돌렸다.
- v11 01: 새로 쓴 시험의 fixture 순서 결함.

**부하 경합(원인 미확정)**: 전체 시험은 조용할 때 6.5분인데 v11 티켓 검증은 14:27 뒤 평균 10.7분이었다(8회). 12코어에 worker와 검증이 각각 `-P 6`으로 겹친다. 티켓 04의 "전체 시험 3벌 동시 실행"이 일부일 수 있다. 14:27 앞 구간에는 측정 부하가 섞여 있어 뺐다. 검증 제한 20분에 한 번 16.9분까지 갔다.

## 제안 (순서대로)
1. **시험 fixture에서 git shim 우회**: `tests/support.py`에서 `git`이 Apple shim이면 실제 git을 찾아 PATH 앞에 둔다. worker의 좁은 시험, 검증, CI를 한 곳으로 덮고 리눅스에서는 하는 일이 없다. 일이 작고 위험이 낮다. 측정한 `CommandLineTools/usr/bin`에는 `python3`, `pip3`, `make`, `cc`도 있어 그대로 앞에 두면 이것들을 가린다. git만 있는 임시 디렉터리에 링크를 두는 방법이 먼저 시도할 만하며, 링크로 git의 하위 명령이 도는지 확인해야 한다.
2. **검증 실패 시 같은 브랜치에서 수리**: 실패 로그를 주고 같은 worktree에서 고치게 한다. `out-of-scope/repair-worker.md`의 다시 볼 조건은 마무리 실패와 병합 충돌만 본다. 티켓 검증 실패의 재시도 비용까지 보도록 고칠지 grill에서 정한다.
3. **worker의 전체 시험 제거**: 수정 worker부터 시험한다. gs가 어차피 병합 트리에서 다시 돌린다. 2가 없으면 실패 한 번이 새 시도 전체가 되어 손해일 수 있다. 실패율을 보며 넓힌다.
4. **싼 검사 먼저**: `xargs`는 실패해도 나머지 파일을 다 돈다. 1초 걸리는 `test_skills` 실패를 알려고 6.5분을 쓴다. 싼 파일을 먼저 돌리고 `&&`로 잇는다.
5. **전체 시험 동시 수 제한**: 경합을 먼저 잰 뒤 정한다. 머신 공용 잠금은 `out-of-scope/machine-wide-lock.md`와 함께 본다.
6. **더 줄이기**: 시험당 git 호출 수를 줄인다(시험용 레포 재사용, 끝까지 도는 시나리오를 함수 단위 시험으로). 아직 재지 않았다.

## 하지 않아도 되는 것
- `max_workers` 올리기: 그래프 폭이 상한이라 효과가 없다.
- 검증을 루프 밖으로: `out-of-scope/async-verify.md`의 판단이 맞다. 재생 효과가 0~-1%다.
- fsync·자동 maintenance 끄기: 효과가 거의 없다.

## 한계
- A/B는 이 Mac의 Apple Git(2.54.0)에서만 쟀다. Homebrew git이나 리눅스에서는 이득이 없을 수 있다. 다른 레포에 적용하려면 환경을 가정하지 않게 따로 설계해야 한다.
- 재생은 v9·v10 두 실행뿐이다. v11은 재시작이 섞여 넣지 않았다.
- 1의 효과는 전체 시험만 쟀다. worker 안의 좁은 시험이 같은 비율로 줄어든다는 것은 가정이다.
