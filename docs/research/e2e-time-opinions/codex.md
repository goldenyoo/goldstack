진단은 대체로 맞습니다. **v5의 주병목은 긴 의존 사슬과, 그 사슬에서 반복되는 테스트·리뷰·수정입니다. 충돌 복구부터 구현할 이유는 약합니다.** 다만 빠진 비용이 있습니다. worker와 fix worker도 전체 테스트를 실행하므로, 테스트 비용은 기록의 `verify` 시간보다 훨씬 큽니다.

코드와 v3–v5의 실제 실행 기록을 읽었습니다. 파일은 수정하지 않았고 테스트도 실행하지 않았습니다.

**1. v5에서 시간을 쓰는 곳**

[state.json](.goldstack/work/goldstack-v5/run/state.json)을 재계산하면, `01→02→03→04→05→06→08` 경로가 실행 구간 전체를 차지합니다.

| 임계 경로의 단계 | 시간 | 전체 284.7분에서 비중 |
|---|---:|---:|
| worker | 128.8분 | 45.3% |
| 리뷰·지적 분류 | 44.4분 | 15.6% |
| fix worker | 34.6분 | 12.2% |
| 티켓 검증 | 51.6분 | 18.1% |
| feature 마무리 | 25.2분 | 8.9% |

07의 14.8분은 02와 완전히 겹칩니다. 따라서 **07을 아무리 빨리 만들어도 v5 wall time은 줄지 않습니다.** 반면 마지막 문서 티켓 08은 혼자 41.5분을 더합니다.

동시 실행 수를 마지막 마무리 전 구간에 대해 계산하면 v3 약 1.80개, v4 약 2.10개, v5 약 1.06개입니다. 단, 이것은 **실행 중인 티켓 수**입니다. `RUNNING`에는 worker뿐 아니라 리뷰·수정·검증도 포함되므로 실제 AI worker 가동률과는 다릅니다.

추가로 짚어야 할 점은 다섯 가지입니다.

- **빈 슬롯과 스케줄러 유휴는 다릅니다.** v5에서 티켓이 하나도 없는 시간은 거의 전부 마지막 25.2분입니다. 중간에 ready 티켓을 놓쳐 수십 분 쉬었던 실행은 아닙니다. 슬롯을 늘려도 의존 사슬은 그대로입니다.
- **스케줄러는 루프에 돌아왔을 때만 greedy합니다.** [`_loop`](src/gs/go.py:458)는 `_finish`를 동기로 호출하고, `_review`와 `_verify`가 끝나야 다시 frontier를 채웁니다. 기존 worker는 계속 돌지만 완료 결과 처리와 신규 시작은 멈춥니다.
- **기록의 worker 시간이 순수 작업 시간은 아닙니다.** 단계 종료는 실제 프로세스 종료가 아니라 코디네이터가 결과를 처리할 때 찍힙니다. 과거 `exit` 파일 시각과 비교하면 v4의 01 worker에는 약 7.8분, 04 fix에는 약 10.4분의 처리 대기가 포함됩니다. v5에서는 이런 지연이 거의 없습니다. 따라서 스케줄러 개선은 v3·v4형 실행에 더 유효합니다.
- **worker 안의 테스트가 큰 중복입니다.** [`worker.write_brief`](src/gs/worker.py:61)는 커밋 전에 검증 명령을 실행하도록 요구하며, fix도 같은 brief를 받습니다. 실제 v5의 08은 전체 suite를 두 번 실행했습니다. 문서 worker 31분을 전부 문서 작성 시간으로 보면 잘못된 결론이 나옵니다.
- **마무리 25분도 대부분 테스트입니다.** v5 로그에는 integration, integration-final, main에서 각각 약 484초짜리 suite가 있습니다. 앞의 두 HEAD 사이에는 report.md만 바뀌었습니다. 현재 [`finish._verify_final`](src/gs/finish.py:295)은 이 경우 검증을 생략하므로, 같은 조건이면 이미 약 8분 줄어야 합니다. 과거 실행 엔진과 현재 코드의 차이를 분리해야 합니다.

현재 충돌 처리에 대한 설명은 정확합니다. [`_catch_up`](src/gs/go.py:889)은 충돌을 abort하고 로그를 남깁니다. [`_fail`](src/gs/go.py:906)은 첫 실패를 대기로 돌리고, [`_start`](src/gs/go.py:558)는 최신 integration에서 새 worktree와 브랜치를 만듭니다. 두 번째 실패는 티켓 실패이며, 실패 worktree는 보존됩니다.

다만 **재시도 0회는 현재 직렬화 정책의 결과**입니다. 같은 파일을 병렬화했을 때도 충돌이 드물 것이라는 근거는 아닙니다.

**2. 후보별 평가**

**① Grill에 임계 경로·예상 동시성 표시: 찬성. “먼저 모듈 분리”는 조건부입니다.**

현재 [`graph.py`](src/gs/graph.py)는 위상 순서와 frontier를 계산합니다. 티켓 예상 시간을 가중치로 넣어 임계 경로를 계산하고, `max_workers=3`과 직렬 검증 제약을 반영한 간단한 실행 시뮬레이션을 추가하면 됩니다. 현재 [`calculate_progress`](src/gs/state.py:154)의 ETA는 평균 티켓 시간에 남은 티켓 수를 곱하고 worker 수로 나누므로, v5 같은 사슬을 제대로 반영하지 못합니다.

작은 직렬 티켓을 합치는 것도 타당합니다. 그러나 절약되는 것은 구현량 전체가 아니라 **문맥 재구축, 리뷰 호출, 반복 검증**입니다. 큰 티켓은 리뷰·수정 범위를 키우므로 무조건 합치면 안 됩니다.

특히 `finish.py`를 여러 파일로 나누어도 squash·CI·보호된 base는 같은 병합·재개 흐름을 바꿉니다. 파일만 달라졌다고 독립 작업이 되지는 않습니다. 선행 리팩터링 자체에도 worker→review→verify 비용이 듭니다.

- v5형 기대 효과: 분해·묶음 조정으로 수십 분 가능하지만 확정치는 없음.
- 비용: 표시 기능은 낮음, 선행 모듈 분리는 중간 이상.
- 권장: [`grill`의 분해 규칙](skills/grill/SKILL.md:20)에 “같은 파일이라 생긴 순서”와 “앞 티켓 결과가 필요해서 생긴 순서”를 구분해서 기록.

**② 기존 `verify_ticket` 사용: 가장 먼저 할 일입니다.**

현재 코드에 바로 맞습니다. [`go._verify`](src/gs/go.py:932)는 최신 integration을 반영한 티켓 worktree에서 `verify_ticket`을 실행합니다. worker와 fix brief도 같은 명령을 사용합니다. integration과 main에서는 전체 `verify`가 유지됩니다.

v5 임계 경로의 코디네이터 검증 51.6분을 티켓당 1–2분으로 줄이면 **여기서만 약 38–45분** 절약됩니다. worker·fix 내부의 전체 suite 반복까지 줄이면 추가 절약이 큽니다.

주의할 점은 현재 키가 **티켓별이 아니라 feature별 명령 하나**라는 것입니다. 티켓마다 다른 테스트를 자동 선택하는 기능은 없습니다. 우선 공통 빠른 검증을 정하고, worker에게 티켓 관련 테스트를 추가 실행하도록 명시하는 정도가 간단합니다.

위험은 통합 회귀 발견이 늦어진다는 것입니다. [`finish.run`](src/gs/finish.py:707)의 전체 검증이 실패하면 자동으로 원인 티켓을 고쳐 주지 않습니다. 빠른 검증에는 변경 영역의 핵심 시나리오를 포함해야 합니다.

**③ 테스트 병렬 실행: 유효하지만 프로세스로 해야 합니다.**

읽은 테스트들은 임시 레포·가짜 원격·가짜 CLI를 많이 사용합니다. 병렬화에 유리한 기반입니다. 하지만 [`test_go.setUp`](tests/test_go.py:189)과 [`support.isolate_git_env`](tests/support.py:6)는 `os.environ`을 바꾸며, cwd를 바꾸는 테스트도 있습니다. **한 프로세스 안의 스레드 병렬 실행은 맞지 않습니다.**

테스트 모듈을 서로 겹치지 않는 2–3개 프로세스 shard로 나누고, 각각 별도 로그를 남기며 모두 통과해야 성공하게 하는 방식이 적합합니다. 모듈 수가 아니라 측정한 소요 시간으로 균형을 맞춰야 합니다.

- 원래 v5 구성에서는 반복 suite가 많아 큰 효과가 날 수 있습니다.
- ②를 적용한 뒤에는 남은 integration·main 검증 등이 주대상이므로 추가 효과는 작아집니다.
- 시간 제한·프로세스 종료를 검사하는 테스트가 있어 과한 동시 실행은 flaky를 늘릴 수 있습니다. “3개니까 3배”는 기대하면 안 됩니다.

**④ 느린 두 번째 리뷰어 제외·timeout: 시간 효과는 명확하지만 품질 비용도 실제로 있습니다.**

[`review.run_together`](src/gs/review.py:301)는 두 리뷰와 각자의 지적 분류가 모두 끝날 때까지 기다립니다. 두 시간이 더해지는 것이 아니라 느린 쪽이 결정합니다.

v5의 02·04에서 primary 리뷰·분류는 각각 약 3분이었고, 전체 리뷰 단계는 15.4분·16.5분이었습니다. 두 번째 리뷰를 빼면 **직접 대기 시간 약 25.8분**이 줄어듭니다.

그러나 실제 기록에서 **02의 fix 지적은 agy만 냈습니다.** primary codex에는 fix 지적이 없었습니다. 따라서 “느리기만 한 중복 리뷰”라는 평가는 틀립니다. 04에서는 agy의 추가 fix 지적이 없었습니다.

추천은 일괄 제거보다 **위험에 따른 선택**입니다. 일반 티켓은 다른 계열 리뷰 하나, squash·revert·재개처럼 놓치기 쉬운 상태 전이는 두 번째 리뷰를 유지할 근거가 있습니다.

짧은 timeout은 구현량은 작지만, 현재 설정은 리뷰 전체에 공통입니다. 두 번째 리뷰어만 제한하려면 구분이 필요합니다. 또한 리뷰 실패는 대체로 verify만으로 진행하므로 timeout은 품질을 낮추는 정책 변경입니다. [`_call`](src/gs/review.py:161)의 종료 처리도 verify의 프로세스 그룹 종료와 다릅니다.

**⑤ 같은 파일 낙관적 병렬화 + 충돌 해결 worker: 장기 후보이며 첫 개선으로는 비추천합니다.**

전체 재구현보다 충돌 부분을 고치는 편이 싸다는 방향은 맞습니다. 하지만 현재 코드에서는 단순히 worker 호출 하나를 추가하는 변경이 아닙니다.

필요한 흐름은 다음과 같습니다.

1. `_catch_up`에서 충돌 상태와 대상 integration SHA를 보존한다.
2. 해결 worker를 별도 실행 단계로 관리하고 코디네이터 루프로 돌아온다.
3. 충돌 해소·커밋·기존 구현 보존을 확인한다.
4. 리뷰·검증 후 병합한다. 그사이 integration이 바뀌면 다시 판단한다.
5. 중단·재개·timeout·실패 시 충돌 상태를 어떻게 복원할지 정의한다.

**“해결 diff만 재리뷰”는 부족합니다.** 현재 리뷰는 catch-up 이전에 수행되고, fix 결과도 재리뷰하지 않습니다. 충돌 해결 변경만 보면 원래 티켓 의도가 사라졌거나 다른 티켓과 의미가 어긋난 것을 놓칠 수 있습니다. 고정한 integration 기준으로 최종 티켓 효과를 리뷰하고 양쪽 완료 조건을 함께 확인하는 편이 맞습니다. [`review.write_diff`](src/gs/review.py:232)의 기준 SHA도 명확히 고정해야 합니다.

자동 merge에 성공한 의미 충돌은 이 worker가 아예 실행되지 않으므로 해결되지 않습니다. v5의 squash·보호된 base·CI·setup·verify는 실제로 같은 상태 전이를 건드립니다. 전부 병렬로 풀 수 있다는 전제도 약합니다.

**3. 추가로 고려할 대안**

| 대안 | 이 코드에서의 구체적 방식 | 판단 |
|---|---|---|
| 리뷰를 비동기로 처리 | `_review` 작업은 결과만 반환하게 하고, `_loop`가 worker 완료·리뷰 완료를 계속 수집. state 변경과 integration 병합은 코디네이터 한 곳에서 수행 | v3·v4의 처리 대기에 효과. v5의 긴 사슬 자체에는 효과 작음 |
| 검증 중 독립 티켓 시작 | integration 검증은 한 개만 유지하되, 기다리는 동안 이미 ready인 티켓의 `_start` 허용 | 기존 의존 의미를 유지하는 비교적 안전한 파이프라인 |
| 의존 티켓을 선행 브랜치에서 조기 시작 | A의 고정 커밋에서 B worktree 생성. B의 병합은 A가 MERGED가 될 때까지 금지. A 수정 시 B catch-up, A 실패 시 후손 무효화 | 가능하지만 branch 기준·리뷰 diff·재개·실패 전파가 복잡함 |
| 문서를 일찍 준비 | spec에서 확정된 사용법·키·구조 문서는 먼저 작성하고, 마지막에는 실제 출력·링크·동작 차이만 동기화 | v5의 08이 41.5분짜리 마지막 장벽이 된 문제를 직접 줄임 |
| 의미 의존과 파일 배타 실행 분리 | `blocked_by`는 결과 의존에 사용하고, 별도 경로/자원 잠금으로 겹치는 작업만 동시 실행 금지 | 불필요한 전이 의존을 줄일 수 있음. 모두 finish.py를 만지는 v5에는 한계 |
| 검증 실패를 먼저 수리 | `_fail`로 전체 재구현하기 전에 같은 브랜치에서 검증 로그를 받은 제한된 repair worker 실행 | 재시도가 있는 실행에 유효. v3–v5 직접 절약은 0 |

선행 브랜치에서 시작하는 stacking은 특히 구분해야 합니다. **의존 티켓 B를 A의 검증 중 시작하려면 B가 A의 미검증 결과를 사용하는 투기 실행입니다.** `_frontier`의 MERGED 조건만 느슨하게 바꾸면 안 됩니다. [`_start`](src/gs/go.py:586)의 시작 SHA, `Active.base`, 리뷰 기준과 실패 전파를 함께 바꿔야 합니다. 빠른 티켓 검증을 도입하면 이 방식으로 숨길 수 있는 검증 시간도 줄어드므로 우선순위가 더 낮아집니다.

임계 경로 순서로 스케줄링하는 것은 비교적 간단합니다. `_frontier`와 완료 결과 처리에서 ID 대신 **남은 후속 경로가 긴 티켓**을 우선하면 됩니다. 다만 v5에서는 사실상 선택지가 없어 거의 절약되지 않습니다.

리뷰→수정 순서는 유지하는 것이 맞습니다. 리뷰가 끝나기 전에 수정할 수는 없습니다. 대신 현재 수정 worker가 별도 문맥을 다시 만들고 테스트까지 수행하는 비용을 줄여야 합니다. 검증을 리뷰 전에 한 번 더 추가하는 것은, 실패가 없었던 이 세 실행에서는 비용만 늘립니다.

**4. 추천 순서와 예상 시간**

먼저 현재 엔진의 보고서 전용 재검증 생략이 실제 사용되는지 확인해야 합니다. 이것은 새 기능이 아니라 이미 구현된 절약이며, v5 기준 약 8분입니다.

그 위에서 다음 네 가지를 추천합니다. 아래 누적 시간은 **빠른 검증 1–2분, 비슷한 구현 작업량**을 가정한 계획값입니다. 단계별 절약을 중복해서 더하지 않았습니다.

| 순서 | 변경 | v5형 누적 wall 예상 |
|---|---|---:|
| 1 | 기존 `verify_ticket` 적용. worker·fix의 반복 전체 suite까지 빠른 검증으로 전환 | **170–210분** |
| 2 | 일반 티켓은 리뷰 하나. 두 번째 리뷰는 위험한 상태 전이 티켓에 선택적으로 사용 | **150–195분** |
| 3 | grill에서 가중 임계 경로 표시, 작은 직렬 작업 묶기, 문서 준비 앞당기기 | **130–180분** |
| 4 | 측정 후 전체 suite를 2–3개 프로세스로 분할 | **120–170분** |

**첫 목표는 285분→150–180분 정도가 타당합니다.** 충돌 해결 worker나 투기 실행 없이도 도달할 가능성이 있습니다. 100분 이하를 약속할 근거는 없습니다. 특히 1번의 추가 절약은 worker 내부에서 얼마나 많은 전체 테스트가 실제로 제거되는지에 달려 있습니다.

확인을 위해서는 다음을 측정하면 됩니다.

- **실제 프로세스 종료와 처리 대기 분리:** `worker_exited_at`, `result_handled_at`, `ready_at`, `started_at`.
- **테스트 호출별 시간:** worker·fix·코디네이터 각각에서 명령, 대상 SHA, 소요 시간, 재실행 이유 기록.
- **리뷰어별 가치와 지연:** 리뷰·분류 시간, 두 번째 리뷰만 발견한 채택 지적, 수정 비용.
- **마무리 세부 시간:** integration verify, 보고서 생성, CI 대기, main verify, 최종 보고서 반영.
- **검증 축소의 부작용:** 빠른 검증 통과 후 integration 실패율, 원인 추적·수리까지 걸린 시간.
- **실행 엔진 식별:** 버전·코드 revision·설정 기록. 자기 자신을 개발하는 도구이므로 실행 대상 코드와 코디네이터 버전이 다를 수 있습니다.

우선 테스트 중복과 리뷰 대기를 줄이고, 그다음 남은 임계 경로를 다시 보겠습니다. 현재 자료로는 복잡한 충돌 복구보다 이 순서의 기대 이득이 훨씬 확실합니다.
